Kafka-as-a-Service

Service owner and technical lead of a managed, multi-tenant Kafka platform built for Airtel B2B Cloud customers — architecture, technology choices, and service readiness, built as a modern product end to end rather than a cluster handed over with a README.

Kafka-as-a-Service React Java Spring Boot Temporal PostgreSQL + Redis Helm + Argo CD

The problem

Airtel B2B Cloud customers need self-serve access to Kafka without each one standing up and operating their own cluster — the same problem the earlier bare-metal Kafka platform solved for internal teams, now as a product other businesses can provision, with the multi-tenancy, isolation, and support model that requires.

Provisioning a tenant's Kafka environment touches many systems — cluster creation, topic and ACL setup, quota enforcement — and these steps can take minutes and fail partway through. A simple request/response API isn't enough; a failure needs to resume safely rather than leave a tenant half-provisioned.

I own the technical direction: architecture, technology choices, pull-request reviews, security and bug analysis, and checking service readiness before each release. Being the service owner doesn't mean I wrote every component — developers and DevOps engineers on the team build alongside me.

Design decisions

Temporal for long-running provisioning workflows. Provisioning a tenant's Kafka environment is a multi-step process that can take minutes and fail partway through. Rather than track progress with ad-hoc database flags, provisioning runs as a durable Temporal workflow — each step retries independently, state survives a service restart, and a partially-provisioned tenant resumes exactly where it left off instead of getting stuck.

Smithy for a contract-first API. Keeping frontend and backend in agreement is otherwise an easy place to drift. The API contract is defined in Smithy first, so client and server code are generated from one schema — a single source of truth instead of two things kept in sync by hand.

PostgreSQL for durability, Redis for pace. Tenant and provisioning state lives in PostgreSQL; Redis handles caching and rate limits so one noisy tenant can't starve the control plane for everyone else.

The same central delivery pipeline as everything else. Jenkins runs software-composition, code, and image security scans (Black Duck, Coverity, Wiz) on every change, and Argo CD handles deployment — the same central CI/CD framework used across the organisation, not a one-off pipeline built just for this service. I use Claude Code for pull-request review and security analysis on this service's provisioner, and to check that frontend and backend requests stay in agreement.
